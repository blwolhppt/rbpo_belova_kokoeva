### Контекст и пользователи

HelpHealth разработан студентом(Белова О.И.), как индивидуальная курсовая работа первого года магистратуры. 
На текущем этапе продукт является учебным прототипом. Отдельных команд эксплуатации, QA, DevOps у проекта нет, а разработка и сопровождение выполнялись самостоятельно. Архитектурные и функциональные решения принимались в рамках целей курсовой работы.
Целевой контекст возможного применения - поликлиники, частные медицинские центры и телемедицинские сервисы. Пациент использует Android-приложение дома, в том числе между очными приёмами, а врач работает с данными через web-интерфейс. Особое внимание в работе уделено пожилым людям, пациентам с хроническими заболеваниями и жителям удалённых территорий.

HelpHealth предназначен для дистанционного наблюдения за состоянием пациентов из групп риска и для организации постоянного информационного взаимодействия между пациентом и врачом.

**Основные функции продукта:**
- регистрация и аутентификация пациентов и врачей
- привязка пациента к врачу по шестизначному коду
- получение и хранение показателей здоровья: пульса, SpO2, температуры, количества шагов, параметров сна и уровня стресса
- ручное ведение пациентом дневника самочувствия
- локальное хранение данных в Android-приложении и предусмотренная синхронизация с сервером
- загрузка медицинских документов, включая PDF-файлы с результатами лабораторных анализов
- извлечение структурированных показателей из лабораторных отчётов с помощью локального LLM/VLM-сервера
- просмотр врачом списка закреплённых пациентов, медицинских данных, дневника, документов и динамики показателей
- создание врачебных записей и рекомендаций для пациента
- уведомление врача об изменениях в данных пациента
- ведение записей на очный приём
- визуализация показателей и результатов анализов в web-интерфейсе

Результатом для пациента является единая точка ввода и просмотра данных о здоровье и получения рекомендаций врача. Врач получает централизованное представление динамики состояния своих пациентов между очными приемами.

**Пользователи**
- Пациент: регистрируется в Android-приложении, вводит данные дневника, передаёт показатели здоровья, загружает медицинские документы и читает записи врача
- Врач: работает через web-приложение, привязывает пациентов, просматривает их показатели и документы, анализирует динамику, создаёт записи и планирует приёмы

**Заинтересованные стороны**
- авторы курсовой работы
- потенциальные медицинские организации и телемедицинские сервисы
- пациенты из групп риска и их лечащие врачи

### Границы

Это позволяет воспроизводимо рассматривать код прототипа и выполнять улучшения, не включая недоступную инфраструктуру и не обрабатывая реальные данные пациентов.


### Компоненты, взаимодействия и границы доверия
**Основные компоненты**
1. Мобильное Android-приложение пациента

   Реализует регистрацию и вход, отображение показателей здоровья, дневник, загрузку документов и просмотр записей врача. Используется Retrofit/OkHttp для REST API и Room для локальных данных
2. Web-приложение врача

   React для регистрации и аутентификации врача, управления списком пациентов, просмотра медицинской карты, графиков, документов, уведомлений и записей на приём
3. Backend API

   Модульный монолит на Django REST Framework. Содержит бизнес-логику, REST эндпоинты, валидацию, разграничение ролей, обработку документов и создание уведомлений
4. PostgreSQL

   Хранит профили врачей и пациентов, связи между ними, диагнозы, показатели устройств, дневники, метаданные документов, результаты анализов, врачебные записи, уведомления и приёмы
5. Файловое хранилище

   Хранит загруженные документы и медиафайлы в volume приложения
6. Модуль обработки лабораторных PDF

   Извлекает текст из PDF с помощью `pdfplumber`, отправляет его локальному LLM/VLM-сервису, проверяет JSON-ответ и сопоставляет показатели со справочником анализов

7. Компоненты развёртывания

   Docker Compose, контейнер backend с Gunicorn, контейнер web-приложения с Nginx и контейнер PostgreSQL

**Внешние системы и сервисы**
- носимое устройство или любой другой источник показателей
- SMTP-сервис для отправки подтверждения электронной почты
- локально развёрнутый Ollama-сервер с OpenAI-совместимым API
- виртуальная машина для развёртывания
- Android-устройство пациента и браузер врача
- GitLab-репозиторий

**Существенные границы доверия проходят между**
- пользовательскими устройствами и API
- ролями врача и пациента
- backend и хранилищами
- backend и внешними SMTP и VLM-сервисами.

**Границы доверия**
- Граница доверия 1

*Между:* устройством пациента или браузером врача и публичным интерфейсом HelpHealth

*Что пересекает границу:* учётные данные, токены, REST-запросы и ответы, показатели здоровья, дневниковые записи, документы и врачебные рекомендации

*Почему граница существенна:* пользовательские устройства и сеть не контролируются серверной частью; все входные данные должны считаться недоверенными, а соединение должно быть защищено

- Граница доверия 2

*Между:* ролью пациента, ролью врача и отношением привязки конкретного пациента к конкретному врачу

*Что пересекает границу:* идентификатор/код пациента, медицинские показатели, документы, записи и команды изменения данных

*Почему граница существенна:* данные пациента должны быть доступны только самому пациенту и уполномоченному врачу. Ошибка аутентификации, авторизации или фильтрации queryset может раскрыть либо изменить чужие медицинские данные

- Граница доверия 3

*Между:* backend API и PostgreSQL/файловым хранилищем.  

*Что пересекает границу:* персональные данные, медицинские показатели, документы, учётные данные, токены и служебные метаданные

*Почему граница существенна:* хранилища содержат основной массив чувствительных данных; важны аутентификация сервиса, минимальные привилегии, резервное копирование, шифрование и контроль доступа к volumes

- Граница доверия 4

*Между:* backend и локальным Ollama/VLM-сервисом

*Что пересекает границу:* извлечённый из лабораторного PDF текст и сформированный моделью JSON с медицинскими показателями

*Почему граница существенна:* мед.данные не должны покидать контур; результат модели требует проверки формата, значений и привязки к пациенту

- Граница доверия 5

*Между:** Android-приложением, локальным хранилищем устройства и источником показателей носимого устройства

*Что пересекает границу:* показатели здоровья, локальные записи, идентификатор пациента и токен сессии

*Почему граница существенна:* физическое устройство пациента находится вне контроля разработчика, данные могут быть подменены, утрачены или прочитаны при компрометации телефона

- Граница доверия 6

*Между:* средой разработки/исходным кодом и средой развёртывания 

*Что пересекает границу:* исходный код, зависимости, контейнерные образы, конфигурация

*Почему граница существенна:* в архиве отсутствует CI/CD и подтверждённая цепочка происхождения артефактов, ошибки или компрометация сборки могут попасть в развёрнутый экземпляр

### Активы и существенные риски

- **Актив:** медицинские данные и документы пациента    
  **Что может произойти:** посторонний пользователь прочитает их по чужому идентификатору   
  **Почему это существенно:** раскрываются диагнозы, анализы и личные сведения; нужны проверки доступа на сервере

- **Актив:** показатели здоровья и врачебные записи   
  **Что может произойти:** данные будут изменены другим пользователем или ошибочно извлечены из PDF   
  **Почему это существенно:** врач получит недостоверную информацию; необходимо проверять владельца записи и результат обработки документа   

- **Актив:** пароли, токены и ключи сервисов   
  **Что может произойти:** значения попадут в исходники, ответы API или журналы   
  **Почему это существенно:** злоумышленник сможет действовать от имени пользователя или сервиса   

- **Актив:** доступность API и обработчика PDF   
  **Что может произойти:** большой файл или множество заданий исчерпают ресурсы сервера   
  **Почему это существенно:** пациенты и врачи потеряют доступ к системе; нужны ограничения размера и числа заданий

## 2. Методологическая основа

**Основная рамка:** OWASP SAMM 2.0 (Software Assurance Maturity Model), отдельные практики с целевым уровнем зрелости 1 (https://owaspsamm.org/model/)
**Дополнительные источники:** OWASP ASVS 5.0.0: для формулирования требований к аутентификации, авторизации и защите данных API; Федеральный закон № 152-ФЗ «О персональных данных»: для учёта требований, связанных с обработкой персональных данных.

**Почему выбрана эта основа:** OWASP SAMM 2.0 позволяет структурировать практики безопасности на всех этапах жизненного цикла разработки. Для системы, обрабатывающей персональные и медицинские данные пациентов и обеспечивающей дистанционное взаимодействие «врач–пациент», важно реализовать технические меры защиты и выстроить процесс: определить требования безопасности на этапе проектирования, обеспечить безопасную сборку и развёртывание, провести верификацию. SAMM даёт практико-ориентированную структуру, которую можно адаптировать под наш проект и соотнести с конкретными артефактами работы (требованиями, архитектурой, тестами, развёртыванием)
**Что ещё рассматривали:** NIST SSDF 1.1 не подходит, так как ориентирован на организационный процесс и требует более зрелой инфраструктуры, чем доступно в рамках нашей курсовой работы; OWASP Top 10 тоже не подходит, так как это перечень рисков без процессного каркаса, недостаточный для назначения ответственности и условий выпуска

**SAMM Design - Threat Assessment (TA), целевой уровень 1**   
*Что требует:* выявить основные угрозы для компонентов и потоков данных   
*Почему применимо:* система обрабатывает медицинские данные через API, БД и VLM-сервис   
*Во что превращается:* анализ угроз несанкционированного доступа, SQL-инъекций и утечки данных   
*Как команда поймёт, что выполнено:* для основных угроз определены меры защиты или проверки   

**SAMM Design - Architecture Assessment (AA), целевой уровень 1**   
*Что требует:* оценить архитектуру с точки зрения безопасности   
*Почему применимо:* чувствительные данные передаются между несколькими компонентами системы   
*Во что превращается:* анализ C4-диаграмм, потоков данных и границ доверия   
*Как команда поймёт, что выполнено:* определены риски архитектуры и меры их снижения   

**SAMM Implementation - Secure Build (SB), целевой уровень 1**   
*Что требует:* обеспечить контролируемую и воспроизводимую сборку   
*Почему применимо:* проект использует Django, React, PostgreSQL, Docker и сторонние зависимости   
*Во что превращается:* Poetry/npm, lock-файлы, Dockerfile и Docker Compose   
*Как команда поймёт, что выполнено:* зависимости зафиксированы, проект воспроизводимо собирается из репозитория   

**SAMM Implementation - Secure Deployment (SD), целевой уровень 1**   
*Что требует:* определить требования безопасности для production-развёртывания   
*Почему применимо:* система размещается на виртуальной машине и доступна через сеть   
*Во что превращается:* хранение секретов вне кода, ограничение открытых портов, настройка HTTPS/TLS и production-конфигурации   
*Как команда поймёт, что выполнено:* конфигурация проверена, секретов нет в репозитории, HTTPS и сетевые ограничения подтверждены проверкой   

**SAMM Verification - Security Testing (ST), целевой уровень 1**    
*Что требует:* проверять требования безопасности тестами   
*Почему применимо:* особенно важны аутентификация, авторизация и разграничение доступа к медицинским данным   
*Во что превращается:* тесты JWT, ролей patient/doctor, доступа только к своим данным, SQL-инъекций и XSS   
*Как команда поймёт, что выполнено:* тестовые сценарии выполнены, результаты зафиксированы в разделе тестирования

### Существенные разрывы

- **Разрыв:** R1 - медицинские маршруты наследуют AllowAny, а выборки ряда обработчиков не ограничены пользователем   
  **Почему важен:** возможен доступ к чужим данным; простое включение IsAuthenticated не решает всё: Android использует Token, а в целом к проекту подключена JWT-аутентификация  
  **Свидетельство:** backend/backend/settings.py:111-119; backend/api/views.py:167–182, 311–454  
  **Приоритет:** высокий   

- **Разрыв:** R2 - PatientSerializer включает все поля пациента, в том числе токен и поле хеша пароля    
  **Почему важен:** секретные данные могут попасть в прямые и вложенные ответы API  
  **Свидетельство:** backend/api/serializers.py:119–133, backend/api/models.py:261–292  
  **Приоритет:** высокий

- **Разрыв:** R3 - Android использует HTTP и журналирование BODY  
  **Почему важен:** медицинские данные могут раскрыться в сети и журналах  
  **Свидетельство:** NetworkModule.kt:15–24  
  **Приоритет:** средний

- **Разрыв:** R4 - проверки PDF находятся в сериализаторе, который не используется загрузкой; ответ LLM проверяется неполно  
  **Почему важен:** возможны недопустимые файлы, перегрузка и сохранение неверных результатов  
  **Свидетельство:** backend/api/serializers.py:136–168, backend/api/views.py:283–363, backend/api/function/conv.py:69–79;  
  **Приоритет:** средний
  

## 4. Целевой Secure SDLC

- **Обязательные практики:** зафиксировать версию и правила доступа; проверить изменения, секреты и настройки; выполнить тесты доступа; сохранить решение о выпуске. При изменении PDF добавляются проверки формата, размера и ответа модели; при сетевом размещении - HTTPS и выдачи файлов; при смене зависимостей - проверка известных уязвимостей
- **Ответственные:** предлагается закрепить за Беловой О.И. правила доступа и исправление API, за Кокоевой М.Р. - тесты, конфигурацию и проверку секретов. Каждая проверяет результат сокомандника; решение о выпуске принимается совместно
- **Результаты:** правила доступа, commit изменения, команды и версии проверок, результаты до/после, список незакрытых проблем и решение о выпуске
- **Контрольные точки:** до реализации согласованы права и тесты; до принятия изменения партнёр проверил код; до выпуска повторены тесты на том же commit; не выполненная проверка не считается успешной; чужой доступ и раскрытие секретов блокируют выпуск
- **Исключения:** записываются риск, причина отсрочки, ограничение, ответственный и срок до следующего выпуска; требуется согласие обеих сокомандниц; высокий риск не принимается для работающей функции: её отключают либо откладывают выпуск; при разногласии выпуск откладывается
- **Объём курса:** локальный стенд с синтетическими данными, исправление прав доступа и секретных полей, тесты двух пациентов и двух врачей, повтор сокомандником

## 5. Технологический профиль
### Метод 1: Интеграционное тестирование аутентификации и разграничения доступа API

**Риск или свойство:** R1 и R2: медицинские API-маршруты допускают недостаточно ограниченный доступ, а сериализатор пациента может раскрывать служебные и секретные поля. Для системы критично, чтобы пациент имел доступ только к собственным данным, а врач - только к данным закрепленных за ним пациентов   
**Цель:** проверить серверное разграничение доступа независимо от поведения web- и Android-клиентов и подтвердить, что знание идентификатора чужого объекта не позволяет прочитать или изменить его данные   
**Область проверки:** аутентификация врача и пациента; PatientViewSet, дневники, показатели устройств, документы, результаты анализов, врачебные записи, уведомления и приемы; сериализация данных пациента  
**Этап жизненного цикла:** Проверка - тестирование безопасности; после внесения исправлений тестирование повторяется перед принятием решения о выпуске  
**Способ или инструмент и версия:** встроенный test runner Django 4.2 и средства тестирования Django REST Framework. Точная patch-версия Django и DRF фиксируется при практической апробации из окружения проекта. Дополнительно отдельные сценарии могут повторяться HTTP-запросами через curl. Для тестов создается минимальная матрица доступа: два врача и два пациента. Проверяются запросы владельца ресурса, связанного врача, другого врача, другого пациента и незарегистрированного пользователя. Для операций чтения и изменения фиксируются ожидаемые HTTP-коды и состав ответа  
**Ведущий участник:** Белова Ольга  
**Как партнер проверит результат:** Кокоева Мария повторяет ключевые негативные сценарии по сохраненной матрице доступа, используя те же тестовые данные, но независимо выполняя запросы. Дополнительно проверяет, что тесты действительно обращаются к объектам другого пациента/врача, а не только проверяют отсутствие токена   
**Ожидаемые свидетельства:** 
- таблица ролей и разрешенных операций   
- исходный код автоматизированных тестов   
- результаты тестов до исправления   
- примеры ответов, подтверждающих возможность чужого доступа или раскрытие лишних полей   
- результаты тех же тестов после исправления   
- подтверждение отсутствия в API-ответах password, authtoken и других служебных полей   
- commit с изменением правил доступа
  
**Что метод не покрывает:** не доказывает отсутствие всех уязвимостей API, не проверяет безопасность транспортного уровня, уязвимости сторонних библиотек и устойчивость системы к нагрузке   


### Метод 2: Статический анализ backend-кода и поиск секретов

**Риск или свойство:** секретные значения и чувствительные настройки могут находиться непосредственно в исходном коде; небезопасные конструкции могут не проявляться в обычных функциональных тестах  
**Цель:** обнаружить потенциально небезопасные конструкции в Python-коде и проверить репозиторий на наличие паролей, токенов, ключей и других секретов     
**Область проверки:** каталог backend/, конфигурация Django, обработчики API, модуль обработки PDF, файлы конфигурации и история/рабочее дерево репозитория  
**Этап жизненного цикла:** Реализация - безопасная сборка и безопасное развертывание; результаты проверки также используются на этапе верификации  
**Способ или инструмент и версия:** Gitleaks 8.30.1 для поиска секретов в репозитории; Bandit 1.9.4 для статического анализа кода; ручная проверка найденных результатов с проверкой соответствующих участков исходного кода   
**Ведущий участник:** Белова Ольга  
**Как партнёр проверит результат:** Кокоева Мария просматривает все находки высокой и средней значимости, сопоставляет их с исходным кодом и независимо подтверждает либо отклоняет результаты  
**Ожидаемые свидетельства:**   
- отчёт Bandit
- отчёт Gitleaks без публикации самих значений секретов
- таблица проверки: подтверждено/ложное срабатывание/неприменимо
- перечень секретов, которые необходимо заменить и вынести в переменные окружения
- результаты повторного сканирования после исправлений

**Что метод не покрывает:** статический анализ не подтверждает возможность практической эксплуатации проблемы и не проверяет корректность бизнес-логики разграничения доступа. Отсутствие находок Gitleaks также не означает, что в системе отсутствуют все способы раскрытия чувствительных данных

### Метод 3: Проверка deployment- и сетевой конфигурации

**Риск или свойство:** R3, а также связанные с ним риски безопасного развертывания: использование HTTP для передачи чувствительных данных, наличие секретов и адресов сервисов в исходном коде, несогласованные параметры Django, Docker Compose, Nginx и клиентских приложений  
**Цель:** проверить, что конфигурация развертывания не требует хранения секретов в исходниках, сервисы используют согласованные параметры окружения, а передача медицинских и аутентификационных данных не предполагает открытый HTTP в целевой конфигурации     
**Область проверки:** docker-compose.yml, Dockerfile backend и frontend, Django settings.py, Nginx-конфигурация, настройки URL API во frontend, CORS/ALLOWED_HOSTS, настройки PostgreSQL и внешнего LLM/VLM-сервиса    
**Этап жизненного цикла:** Реализация - безопасное развертывание     
**Способ или инструмент и версия:** ручной конфигурационный review совместно с docker compose config и проверочными HTTP-запросами через curl. Проверяется происхождение каждого чувствительного значения: секреты и параметры среды должны поступать из environment variables или отдельного конфигурационного файла, не входящего в репозиторий. Отдельно проверяются сетевые адреса, открытые порты, параметры базы данных, CORS  
**Ведущий участник:** Кокоева Мария  
**Как партнёр проверит результат:** Белова Ольга независимо просматривает итоговую конфигурацию, запускает формирование effective-конфигурации Docker Compose и проверяет, что приложение не зависит от захардкоженных IP-адресов, паролей и других секретных значений    
**Ожидаемые свидетельства:**   
- очищенный от секретов вывод docker compose config   
- перечень найденных несогласованностей конфигурации   
- результаты поиска IP-адресов и секретов
- подтверждение переноса чувствительных параметров в environment variables
- конфигурация HTTPS либо зафиксированное ограничение локального учебного стенда   
- результаты повторной проверки после изменения конфигурации   
**Что метод не покрывает:** локальная проверка конфигурации не подтверждает безопасность реальной облачной инфраструктуры, сертификатов, firewall и других элементов production-среды, доступ к которой отсутствует   

### Метод 4: Негативное тестирование загрузки и обработки лабораторных PDF

**Цель:** убедиться, что endpoint загрузки отклоняет неподдерживаемые или некорректные файлы, ограничивает входные данные и не сохраняет некорректный результат обработки как достоверные медицинские показатели      
**Область проверки:** endpoint загрузки документов, обработка PDF, pdfplumber, вызов LLM/VLM-сервиса, разбор JSON-ответа, сопоставление показателей со справочником анализов и сохранение результата в БД      
**Этап жизненного цикла:** ...  
**Способ или инструмент и версия:** Проверяются как минимум следующие случаи:   
- корректный PDF
- файл с разрешением .pdf, но неподходящим содержимым
- поврежденный PDF
- файл, превышающий установленное ограничение размера
- пустой файл
- ответ LLM, не являющийся JSON
- JSON с отсутствующими обязательными полями
- неизвестный показатель анализа
- некорректное или выходящее за допустимый формат значение

**Ведущий участник:** Кокоева Мария   
**Как партнёр проверит результат:** Белова Ольга независимо выбирает часть негативных случаев и повторяет тестирование. Дополнительно проверяет, что тест считается успешным только тогда, когда некорректный вход отклонен или безопасно обработан, а не просто не приводит к падению приложения  
**Ожидаемые свидетельства:**   
- набор синтетических PDF/фикстур без реальных медицинских данных   
- исходный код тестов   
- результаты выполнения до исправления   
- подтверждение отклонения некорректных файлов и ответов модели после исправления   
- отсутствие сохранённых некорректных медицинских показателей   
- результаты повторного запуска тех же тестов   
**Что метод не покрывает:** метод не оценивает медицинскую корректность выводов LLM/VLM и не доказывает качество распознавания всех возможных форматов. Нагрузочное тестирование и отказоустойчивость внешнего LLM/VLM-сервиса также остаются вне данной проверки
